# Skill · Grill-Me
**Mode:** On-demand — invoked by any agent before executing a plan

---

## When to invoke

Invoke when you are holding a plan, approach, or implementation
decision and need to work through open questions before execution
begins. The invoking agent decides whether it applies.

**Primary invokers:**
- **Delivery Manager** — burst kickoff (step 6 of build kickoff
  checklist), complex tasks (before assigning to Engineer),
  burst-start planning (after re-entry orientation)
- **Refinement Ceremony** — on the proposed build sequence
  before handoff (step 5 of the "Your job" list)
- **Engineer** — implementation fork mid-task (self-invoke)
- **Architect** — architectural decision review

**This skill is not:**
- A discovery tool — use PM Agent + Devil's Advocate to question
  the problem or user framing
- A scope tool — use feature-triage to decide whether to build
- A review tool — use Reviewer/QA to evaluate completed work

Strictly: *given we are building this, is the plan sound?*

---

## Process

**1. Read the full plan**
Understand the shape before asking anything. Do not start
questioning until you have read every part of the plan.

**2. Check the codebase**
Identify every question the plan raises. For each, check whether
it can be answered by reading files or running a command. Answer
those questions yourself — only ask the human about things you
genuinely cannot resolve from the codebase.

**3. Build a decision tree**
List all remaining open questions. Order them by dependency:
a decision that other decisions depend on must come first. Map
dependencies explicitly before starting.

**4. Work sequentially**
For each question:
- State the question clearly and specifically
- Offer a recommended answer using the format below
- Wait for confirmation, correction, or elaboration
- Do not move to the next question until this one is resolved

**5. Produce a decision log**
Record what was decided and why.

---

## Recommended answer format

> **Recommendation:** [One clear answer]
> **Reasoning:** [One sentence]
> **Assumption:** [What must be true for this to hold]

Always provide a recommendation — never ask an open question
without one. This lets the human accept quickly ("yes, that")
or correct with minimal friction.

---

## Output

```
## Grill-me: [plan name / task title]
**Invoked by:** [agent]
**Context:** pre-build | mid-burst | implementation fork

### Decisions
1. [Question] → [Decision made] _(recommended | corrected | human-directed)_
2. ...

### Unresolved
- [Anything that could not be resolved — flagged for human escalation]

### Plan notes
[Short summary of how the plan changes in light of the decisions — optional]
```

The *(recommended | corrected | human-directed)* tag records whether
the human took the recommended path, overrode it, or drove the answer
themselves. Useful signal for the invoking agent and for future bursts.

### Complex task gate

Before assigning any task you judge too ambiguous to execute
directly, invoke `skills/grill-me.md`. A task is ambiguous if:
- Its acceptance criteria leave room for two different implementations
- It has an unresolved dependency not covered by the build sequence
- The Engineer would need to make a product decision to complete it

Resolve the ambiguity with grill-me before handing off. A task
that enters the Engineer with unresolved ambiguity will either
stall or produce the wrong output.
